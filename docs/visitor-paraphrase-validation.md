# คำถามหลายสำนวนและการตีความเจตนา

เพิ่มชั้นตีความคำถามในตัวทดลอง โดยเปิด `THONGTHAI_VISITOR_UNDERSTANDING=1` ตัวทดลองเปิดค่านี้ให้อัตโนมัติ ส่วนการ deploy ต้องตั้งตัวแปรนี้อย่างชัดเจน การเปลี่ยนแปลงยังไม่ได้ deploy

- คำถามที่รองรับอยู่แล้วใช้แหล่งข้อมูลเดิมโดยไม่เรียก AI เพิ่ม
- คำสะกด/คำศัพท์ที่เทียบความหมายได้ชัดเจนจะปรับเพื่อเลือกหัวข้อ โดยเก็บคำปฏิเสธและข้อจำกัดอาหาร
- คำถามอ้อมใช้โมเดลระบุหัวข้อ ขอบเขต และความมั่นใจเท่านั้น ไม่รับราคา กฎ หรือคำสั่งทำรายการจากโมเดล
- คำถามใหม่ที่ระบุเรื่องชัดเจนไม่ใช้ประวัติเรื่องก่อนหน้า คำอ้างอิง เช่น “แล้วหนึ่งทุ่มล่ะ” ใช้ประวัติผู้ใช้ที่จำเป็นเท่านั้น
- เก็บ cache เฉพาะผลตีความ 10 นาที สูงสุด 100 รายการต่อ process ไม่ cache ราคา/สต๊อก/ผลจอง ประวัติที่ใช้ตีความเป็นส่วนหนึ่งของ cache key
- ชั่วโมงถึงสถานที่เปรียบเทียบกับเวลาทำการปกติที่ผู้ใช้ให้ ไม่รับรองสถานะเปิดสด วันพิเศษ หรือเวลาแต่ละกิจกรรม
- ยังคงวงเงินเดิม การตีความใช้ input reserve ของงาน semantic ที่มีอยู่และ output สูงสุด 160 tokens เมื่อมีการตีความก่อนตอบจากข้อมูล จะปรับ response-turn record ไม่ให้ติดป้าย zero-cost ผิด
- ถ้าไม่มั่นใจจะถามเพิ่ม ถ้า provider ปฏิเสธ key จะไม่ยิง AI ซ้ำต่อใน turn เดียว และพักคำขอยืนยันตัวตนเพิ่ม 60 วินาที ผลตีความที่มีใน cache และทางตอบข้อมูลพื้นฐานยังใช้ได้

ตัวอย่างในชุดทดสอบ: “อินทะนิลอยู่ในทำมาชาติใช่ป่าว”, “เอารถส่วนตัวไป มีที่ให้จอดปะ”, “ลูกกินรสจัดไม่ไหว มีของรสอ่อนๆปะ”, “ขี้ม้าค่ารอบกี่บาท”, “ไปถึงตอนห้าโมงเย็นยังทันไหม”, “แล้วหนึ่งทุ่มล่ะ”

## ผลตรวจ 2026-10-18

ชุดทดสอบล่าสุดผ่าน 152 ข้อ: สำนวนใหม่ 36 แบบทั้ง Web/LINE พร้อมกรณี context, negation, ขอบเขตร้าน/สัตว์เลี้ยง, cache, คำสั่งทำรายการ, log ต้นทุน และ 401 รวมการถามสำนวนทั้งชุดต่อเนื่องในแชตเดียว (จำลองเฉพาะผลตีความจากโมเดล); ชุดคำถามเดิม 28 ข้อแบบแยก/ต่อเนื่อง; และการทดสอบวงเงิน

เมื่อตัว KKU key ยังใช้ได้ เคยลองสำนวนใหม่ผ่าน HTTP จริงครบ 36/36 แบบแยกบทสนทนา รายงานเก็บที่ `/private/tmp/tamma-paraphrases-live.json` การทดสอบต่อเนื่องภายหลังพบปัญหาบริบท/การกันวงเงินและนำมาแก้ แต่การยืนยัน build ล่าสุดกับ KKU ต่อไม่ครบเพราะ endpoint ตอบ **401 Unauthorized** ซึ่งตรวจซ้ำด้วยคำขอสั้นแยกจากแอปแล้ว จึงยังไม่อ้างว่ารอบต่อเนื่องล่าสุดผ่านทั้งหมด หรือวัดบิลจริงของ KKU ได้

ชุดรวมก่อนการปรับรับมือ 401 รอบล่าสุดผ่าน 3,130/3,132 เหลือ Owner draft-expiry ที่เป็นข้อผิดพลาดเดิม และ worker ของ owner-slip-review ล้มระหว่างรันพร้อมกัน (รันแยกผ่าน 53/53)

รันทดสอบในเครื่อง:

```sh
npm run preview:chat:kku
npm run eval:visitor:local -- --paraphrases
npm run eval:visitor:local -- --paraphrases --conversation
```

ต้องมี KKU key ที่ยังใช้ได้ใน `.env.local` และเริ่มตัวทดลองใหม่หลังเปลี่ยน key ไม่ต้องส่ง key ในแชต ชุดทดสอบออฟไลน์ใช้ `node --import tsx --test tests/visitor-paraphrases.test.ts`

การผ่านชุดสำนวนที่ทดสอบไม่รับประกันภาษาไทยทุกสำนวน และไม่ได้เติมข้อเท็จจริงธุรกิจที่ยังไม่มีแหล่งยืนยัน เมนู/ราคาหลังบ้านในตัวทดลองยังเป็นข้อมูลจำลอง

ตรวจ regression ที่เกี่ยวข้องรอบสุดท้ายผ่าน **270/270** ครอบคลุมร้านอาหาร คาเฟ่ local concierge, provider, วงเงิน และชุดคำถามใหม่ แก้การให้หัวข้ออาหารในข้อความปัจจุบันชนะหัวข้อเครื่องดื่มเก่า โดยยังเก็บข้อจำกัดอาหารไว้ การยืนยันแชตยาวกับ KKU หลังแก้บริบทนี้ยังทำไม่ได้เนื่องจากผู้ใช้ยังอัปเดต key ไม่ได้ จึงใช้ผลทดสอบจำลองยืนยันกลไกและรายงานข้อจำกัดแยกไว้ชัดเจน

คำถามพื้นฐานเดิมผ่าน HTTP จริง 28/28 บนตัวทดลองรุ่นใหม่โดยไม่เรียก AI แม้ key ใช้ไม่ได้ ส่วนสำนวนใหม่ที่ต้องตีความด้วยโมเดลต้องรอการยืนยันตัวตน KKU ที่ใช้ได้ก่อน
